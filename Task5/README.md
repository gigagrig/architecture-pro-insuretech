# GraphQL API сервиса client-info

[Схема schema.graphql](schema.graphql) описывает чтение клиентских данных веб-приложением и `core-app`. Предлагаемый адрес — `POST /graphql` сервиса `client-info` по HTTPS. Схема записана на SDL (Schema Definition Language) — языке описания типов GraphQL.

## Соответствие исходному REST API

В Swagger из условия определены три операции чтения и три сущности. Все операции требуют идентификатор клиента.

| REST-операция | Сущность и поля | Запрос в GraphQL |
| --- | --- | --- |
| `GET /clients/{id}` | `Client`: `id`, `name`, `age` | `client(id: $id) { id name age }` |
| `GET /clients/{id}/documents` | `Document`: `id`, `type`, `number`, `issueDate`, `expiryDate` | `client(id: $id) { documents { id type number issueDate expiryDate } }` |
| `GET /clients/{id}/relatives` | `Relative`: `id`, `relationType`, `name`, `age` | `client(id: $id) { relatives { id relationType name age } }` |

Единственный корневой запрос `client(id: ID!)` покрывает все три операции через выбор полей. Документы и родственники доступны как вложенные списки клиента. Можно запросить только один список или сочетание полей из всех трёх ресурсов. В переданном контракте описано только чтение, поэтому схема содержит тип `Query`.

## Типы и поведение ответа

- Идентификаторы имеют тип `ID`, возраст — `Int`, остальные поля — `String`. Значения `type` и `relationType` остаются строками: перечни допустимых значений в Swagger не заданы. Для дат также сохраняется `String`, поскольку исходный контракт не задаёт формат даты.
- Входной `id` обязателен: это обозначено `!`. У полей исходных объектов нет списка `required`, поэтому их значения могут быть `null`; обязательность данных не предполагается.
- Списки имеют типы `[Document!]` и `[Relative!]`: элементы — объекты, сам список допускает `null`. Для существующего клиента без документов или родственников возвращается `[]`. При ошибке чтения списка возвращаются `null` и описание ошибки в `errors`; остальные доступные поля сохраняются в ответе.
- Для несуществующего клиента возвращается `data.client: null`. Это выбранное поведение нового API: исходный Swagger описывает только успешный ответ.

Правила типов и обработки ошибок соответствуют [спецификации GraphQL](https://spec.graphql.org/September2025/).

## Примеры запросов

Карточка для веб-приложения:

```graphql
query ClientCard($id: ID!) {
  client(id: $id) {
    id
    name
    age
  }
}
```

Только документы клиента:

```graphql
query ClientDocuments($id: ID!) {
  client(id: $id) {
    documents {
      id
      type
      number
      issueDate
      expiryDate
    }
  }
}
```

Только родственники клиента:

```graphql
query ClientRelatives($id: ID!) {
  client(id: $id) {
    relatives {
      id
      relationType
      name
      age
    }
  }
}
```

Имя, документы и родственники для сценария `core-app`:

```graphql
query InsuranceClientData($id: ID!) {
  client(id: $id) {
    name
    documents {
      type
      number
    }
    relatives {
      relationType
      name
    }
  }
}
```

Для каждого примера переменные передаются отдельно: `{"id": "client-123"}`. В теле HTTP-запроса используются поля `query` с текстом выбранной операции и `variables` с этим объектом.

## Условия реализации

Обработчики полей (resolvers) загружают документы и родственников только при запросе соответствующих полей. `client-info` проверяет права вызывающего пользователя или сервиса на клиента и запрошенные данные. Ошибка доступа не должна подменяться пустым списком.

В контракт перенесены все поля предоставленного Swagger. Остальные атрибуты большой карточки добавляются после описания их типов и прав доступа. Ограничения размера списков в исходном API отсутствуют; если они вырастут, потребуется отдельно согласовать постраничную выдачу и ограничение объёма запроса.
